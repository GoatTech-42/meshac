## Gap 11: Meteor Slippy (logged 7:51 PM, design only, not coded)
Root cause (Meteor BlockMixin): client-side override of Block.getFriction to the slippy setting (default 1.0, range 0.01-1.10) for every block not blacklisted. Vanilla normal blocks are 0.6, ice 0.98. Effect: on-ground horizontal velocity decays by f*0.91 per tick instead of 0.546, so the player coasts like on ice, and ground acceleration drops (0.216/f^3).
Design: on ground, on a block with known vanilla friction 0.6 (not ice/slime/blue ice/soul sand etc.), next horizontal speed must be <= 0.546*v + max input accel. Sustained coasting above that bound for several ticks with ground contact = slippy. Needs burst/lag tolerance, exemptions for knockback, water/ladder, vehicles, and a vanilla-ice and potion control. Prove on rig: Meteor Slippy at 0.6/0.98/1.1, legit stop-on-stone, legit ice, lag-injected legit.

## Gap 12: Meteor PacketMine (logged 7:53 PM, design only, not coded)
Root cause (Meteor PacketMine.sendMinePackets): sends START_DESTROY_BLOCK then STOP_DESTROY_BLOCK back to back in the same tick (two sequenced packets), then only waits client-side for its own progress estimate. Vanilla sends STOP only after the break delta (hardness, tool, enchants, effects, ground/water) has accumulated over the ticks since START. The vanilla server only checks a loose fraction of expected progress on STOP, so an instant STOP gets accepted for many blocks. It also optionally spams ABORT_DESTROY_BLOCK to hide progress.
Design: per player track START time/pos; on STOP compute vanilla break delta (tool, enchants, haste/fatigue, onGround, underwater) and require elapsed ticks*delta >= ~0.9 (lag-tolerant: use packet arrival burst tolerance). STOP with no START or STOP too early = flag, and cancel the break (server re-sends block). Rig proof: PacketMine on stone/dirt/obsidian with and without a good pickaxe, legit mining control of each, haste/water/lag-injected legit control, creative instabreak exempt.

## Gap 13: Meteor GhostHand (logged 7:56 PM, design only, not coded)
Root cause (Meteor GhostHand): when the player right-clicks and the block in view has no block entity, it marches a ray along the view direction (0.1 steps up to reach) and sends useItemOn at the first chest/container found, hit pos = block center, face UP, ignoring any walls in between. The player really IS aiming at the chest, so meshac Interact.place look check (AABB of the clicked block inflated 0.3 along the view ray) passes: it checks aim, not occlusion.
Design: in Interact.place (and the block-interact path for containers), do a vanilla ClipContext raycast from the eye to the claimed hit point with the collision/outline shape. If a different solid block is hit first (and the target is not reachable from that eye pos), refuse the click and signal. Tolerances: inflate for hit-pos rounding, eye height while sneaking, same-tick lag view (existing 250 ms rotation history), glass/open doors/non-full shapes use the real shape. Rig proof: GhostHand on a chest behind stone, behind glass (legit, must pass), behind a fence/slab (legit), plus legit chest opens and a lag-injected control.
