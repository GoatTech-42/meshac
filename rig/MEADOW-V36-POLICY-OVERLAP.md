## Overlap surface (v36 tip vs meshac bundle tip 0107)
Rig-only drivers (src/rig, not in release builds):
- **NoFallSpoof / NoFallSpoofGate - ALIGNS (good catch-side driver), mechanism corrected 0110.** While airborne past fallDistance>3 (default), sends ServerboundMovePlayerPacket.StatusOnly(onGround=true) every k-th airborne tick (default k=2), honest air position packets between, client fall distance untouched. meshac's statusOnly() path (Movement.java:409-420) scores these on a SEPARATE consecutive counter s.bufStatus - NOT the GroundEvidence 5-claim window (my 0108 text said otherwise; wrong). Per status packet: past grace, no exemption, probe air 0.1 below the CURRENT server box: `s.bufStatus = air ? s.bufStatus + 1 : 0` (:414); at 3 consecutive it signals nofall "ground flag in mid-air" (:417) - that exact text, not "nofall ground spoof". Interleaving matters by packet TYPE: any STATUS packet with onGround=false resets bufStatus to 0 (:410-411); POSITION packets (the honest fall packets between spoofs) do NOT touch it. Predicted: default k=2 interleave flags on the 3rd spoof status packet, provided no StatusOnly(false) intervenes and grace has expired. The GS-A/GS-C rows in 0104 drive the POSITION-claim path (gndEv window, "nofall ground spoof") - a different path from this driver.
- **MicroHop / MicroHopGate - ALIGNS (catch-side driver), corrected 0110: my 0108 F1 was WRONG.** The microhop gate (Movement.java:298) reads s.ground, which is the PRIOR committed claim's ground state (`if (atClaim) { s.dy = s.cy - s.py; s.ground = s.cground; }` at :126) - never the current packet's onGround. An honest small hop from ground therefore DOES enter the gate: prior packets grounded (s.ground=true), hop packet dy=0.10-0.25 inside (0.005, 0.30), the strip 0.03 below the moved box is air when hopping off flat ground (block top is 0.2 below), clean-pad design clears the ceiling and powder guards. bufHop += 2 per hop (:304). Timing honestly derived: MicroHopGate's 15-20 setting is CONSECUTIVE GROUNDED ELIGIBLE ticks (its count resets to 0 whenever not moving, not onGround, or not on a clean pad), NOT the hop-to-hop interval - each hop's airtime (a 0.10-0.25 takeoff, several ticks) sends airborne server packets that also advance meshac's hopClock, which forgives 1 per 30 packets (:307). So the hop-to-hop SERVER PACKET count is the grounded gap plus the airtime, and whether a decay lands between hops is a hopClock phase question, not a "15-20 beats 30" one - that inference is dropped. Derived expectation: the flag needs bufHop >= 3 (:305), i.e. the 2nd hop if no decay fired between, the 3rd or 4th if it did; the exact hop index is NOT derived here (needs the true packet cadence on the rig). Consequence: nb-microhop-cheat from 0103 is UNBLOCKED in principle by this module - PREDICTED catch, exact hop number unverified, UNVERIFIED until the rig run. Residual caveats: (a) each hop must start from server-committed ground - the module gates on CLIENT moving+onGround, which is not the server's committed state; the two are assumed to agree here, not proven (desync can separate them); (b) only the takeoff packet counts (subsequent airborne packets have s.ground=false); (c) the check cannot tell the rig's honest small hops from a cheat's packet hops - no vanilla movement pattern we know produces sustained 0.10-0.25 ground takeoffs (current knowledge, not a proof of impossibility); the known legit guards are the low-ceiling and powder cases (0103 documents both).
